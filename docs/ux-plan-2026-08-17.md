## 1. 결론 요약

### 1.1 "지금 메뉴 카드, 프로덕션에 써도 되나?" — **아니오. 구조적으로 안 된다.**

이유는 취향이 아니라 **물리적으로 대비비를 보장할 수 없기 때문**이다.

현재 `ProductCard`는 사진을 카드 전체에 깔고(`object-cover`), 그 위에 반투명 유리 패널을 얹고, 그 안에 `text-[#191F28]` 하드코딩 잉크색으로 메뉴명·가격을 올린다. 게다가 그 유리 패널에는 `mask-image: linear-gradient(to top, black 30%, transparent 100%)`가 걸려 있어서 **패널의 틴트와 블러가 위로 갈수록 사라진다**. 메뉴명은 패널 하단 30% 구간이 아니라 그 위쪽에 놓이므로, 이름이 실제로 앉는 위치의 유효 틴트 알파는 `0.3 × ~0.7 ≈ 0.21`이다. 즉 **메뉴명은 사실상 생사진 위에 놓인 진한 회색 텍스트**다.

- 사진의 해당 영역이 밝으면 통과, 어두우면 **대비비 1~2:1로 즉시 실패**한다. 사진이 바뀌면 결과가 바뀐다. 검증 불가능한 상태다.
- `text-[#191F28]`은 **리터럴 hex**라서 `.high-contrast` 클래스가 붙어도 바뀌지 않는다. 즉 이 제품의 핵심 기능인 **고대비 모드가 메뉴 화면의 가장 중요한 텍스트에 대해 아무 효과가 없다.**
- 이건 `DESIGN.md`의 "4.5:1 default / 7:1 AAA를 **절대** 밑돌지 않는다", `PRODUCT.md`의 "WCAG 2.2 AA is the enforced floor", `docs/design-system.md`의 "high-contrast mode switches immediately to AAA" 세 곳을 동시에 위반한다.

**부수 위반 3건**:
- 메뉴명 `text-[15px]` — 16px 하한선 위반(§7.2 전체 목록).
- `line-clamp-2` + `aspect-[4/5]` 고정 — `docs/component-standards.md` §1이 명시한 "Fluid Vertical Title Auto-Expansion, `line-clamp-none`"과 **정면 모순**. 가로세로비가 고정이라 카드는 애초에 세로로 늘어날 수 없다.
- 품절 카드에 `opacity-60`이 통째로 걸려 "품절" 배지 대비비가 **3.71:1**로 떨어진다(§7.1).

## 3. 메뉴 카드 레이아웃 — 4개 옵션 비교와 최종 권고

### 3.2 최종 권고: **B를 기본으로, fontScale ≥ 1.15에서 C로 자동 전환**

이유:

1. **B는 A의 유일한 치명적 결함(대비 보장 불가)만 제거하고 나머지 장점을 전부 유지한다.** 사진은 여전히 카드 상단 전체를 채운다(`aspect-[4/3]`, `object-cover`). 사진을 줄이는 게 아니라 텍스트를 사진 밖으로 꺼내는 것뿐이다. ADR 0013(실사진 채택)은 **그대로 유효**하다.
2. **B는 토스 카드 스펙 그 자체다.** `.card { background: var(--bg-base); border: 1px solid var(--border-subtle); border-radius: var(--radius-lg); }` — 흰 채움 + 1px 보더. 지금은 카드 배경이 `product.themeBg` 리터럴 hex라 토큰 밖에 있다.
3. **fontScale 자동 전환은 이 제품에서만 정당화되는, 진짜 차별점이 되는 규칙이다.** 이 앱은 이미 `fontScale`을 스토어에 갖고 있다(`useAccessibilityStore`). "글자를 키우면 레이아웃이 열 수를 줄여 이름이 안 잘린다"는 건 일반 반응형(뷰포트 기준)이 못 하는 일이고, 이 제품의 정체성("장애인도 동일한 정보")에 정확히 부합한다. AI가 만든 일반 스캐폴드에서는 절대 안 나오는 종류의 디테일이다.
4. **C를 기본으로 하지 않는 이유**: ADR 0012가 리스트를 버린 진짜 원인은 "56px 썸네일이 사진에 너무 작다"였다. 96~112px 썸네일이면 그 문제는 없어진다. 다만 18개 메뉴를 1열로 깔면 스크롤이 길어지고, 사진 매력도가 떨어져 카페 메뉴판으로서의 흡인력이 약해진다. 기본 배율에서는 2열이 낫다.
5. **D는 채택하지 않는다.** §5 참조.

### 3.4 왜 "그냥 정사각형 이미지 밑에 텍스트"가 맞는 답인가 (사용자 질문에 대한 직답)

맞다. 그게 정답이다. 다만 **정사각(1:1)이 아니라 4:3**을 권한다:

- 커피/음료 사진은 세로로 긴 잔이 많아 1:1 크롭에서 잔의 위아래가 잘린다. 4:3이 크롭 손실이 가장 적다.
- 1:1 + 텍스트 블록을 붙이면 카드가 세로로 너무 길어져 한 화면에 2행이 안 들어온다. 4:3이면 2행이 들어온다.
- `ProductDetailSheet`의 히어로는 이미 `h-56 sm:h-64` (약 4:3~16:9) — 그리드와 상세의 크롭 인상이 비슷해져 전환이 자연스럽다.

## 4. "카테고리별 box 만들어서 분리" — **권고: 하지 말 것**

현재는 각 카테고리가 `<section>` + `<h2>커피</h2> <span>3개</span>` + 그리드로 되어 있고, 시각적 컨테이너는 없다.

**박스를 씌우면 안 되는 이유:**

1. **보더 이중화.** 카드가 이미 `border-border` + `shadow-resting`을 갖는다(§3.3). 그 바깥에 또 박스 보더를 두르면 `DESIGN.md`의 Border-and-Shadow Rule이 카드마다 두 겹으로 쌓인다. 토스 무드("그림자 거의 없음", 평면 우선)와 정면 충돌한다.
2. **가로 폭 손실.** 360px 뷰포트에서 페이지 `px-4`(32px) + 박스 `p-4`(32px) = 카드 가용폭이 296px → 열당 142px. §3.1에서 계산한 fontScale 1.3 문제가 **더 악화**된다.
3. **이미 있는 문제를 푸는 중복 장치다.** 카테고리 구분은 스티키 카테고리 헤더(§2.1)가 이미 담당하고 있고, 스크롤스파이로 현재 위치까지 표시한다.

**대신 할 것 (구분감은 강화하되 박스는 안 씌운다):**

- 섹션 헤더를 현재 `text-2xl font-black`에서 **좌측 정렬 유지 + 상단 여백 확대**(`gap-8` → `gap-10`)로 리듬을 만든다.
- 섹션 사이에 `Separator`(1px `border-border`)를 **전폭**으로 하나 넣는다. 카드 보더와 두께가 같아도 방향(수평 전폭 vs 카드 사각)이 달라 충돌하지 않는다.
- `<h2>`에 `id`가 이미 있고 `<section aria-labelledby>`가 걸려 있다 — **스크린리더 입장에서는 이미 "박스"가 존재한다.** 시각적 박스는 SR 사용자에게 아무것도 더 주지 않는다. 이 제품 원칙("동일한 정보")상 시각 전용 장치를 추가할 이유가 약하다.
- 카테고리별 개수 `{n}개`가 지금 `aria-hidden`이고 `<h2>`의 `aria-label`에 `총 N개 메뉴`로 들어가 있다 — 이 처리는 **올바르다. 유지.**

## 5. "인기 섹션처럼 좌우 스크롤" — **인기 1개 섹션에만 유지, 카테고리에는 절대 금지**

### 5.1 카테고리 가로 스크롤이 안 되는 이유

- **운동장애 사용자에게 가로 스와이프는 세로 스크롤보다 훨씬 어렵다.** 이 제품의 명시 타깃(`PRODUCT.md`: 휠체어·고령자·운동장애)에 직접 불리하다.
- **스크린리더는 선형이라 시각 순서와 어긋난다.** 시각 사용자는 "3개 중 2개만 보이고 옆에 더 있다"를 스크롤바/페이드로 알지만, SR 사용자는 그냥 순서대로 다 읽는다. 두 경험이 달라진다 — 이 제품이 가장 피해야 할 형태.
- **몇 개인지 모른다.** 세로 그리드는 스크롤 길이로 양을 짐작하지만 가로 스크롤은 못 한다.

### 5.2 현재 인기 섹션의 실제 결함 (지금 고쳐야 함)

```ts
// FeaturedMenuSection.tsx:24-26
const featuredProducts = React.useMemo(() => products.slice(0, 4), [products]);
```

- **"인기"가 아니라 그냥 JSON 파일의 앞 4개다.** 현재 결과: 아메리카노 / 카페라떼 / 바닐라라떼 / 디카페인 아메리카노.
- 바로 아래 "커피 3개" 섹션이 **아메리카노 / 카페라떼 / 바닐라라떼** — **4개 중 3개가 중복.** 화면 최상단 200px가 바로 밑 내용의 복사본이다.
- `docs/features.md`는 "1, 2, 3위 badge"라고 쓰여 있고 ADR 0012는 "BEST badge"라고 쓰여 있는데, 실제 코드는 `1 2 3 4` 숫자 칩이고 그 칩은 `aria-hidden` — **SR 사용자에게 순위 정보가 안 간다.** 단, 버튼 `aria-label`에 `인기 N위 메뉴`가 들어 있어 실질적으로는 전달된다(중복 아님, OK).

**처방:**

1. `menu.json`의 `Product`에 `popularityRank?: number` 필드를 추가하고, 값이 있는 상품만 순위 오름차순으로 노출한다. `slice(0,4)`를 지운다. Phase 1은 시드 데이터이므로 **카테고리를 흩어지게** 지정한다(예: 아메리카노 1 / 뉴욕 치즈케이크 2 / 자몽 에이드 3 / 크로크무슈 4). 그러면 중복 문제와 "인기가 가짜" 문제가 동시에 사라진다.
2. 타입:
   ```ts
   // lib/types/menu.ts
   /** 인기 섹션 노출 순위. 없으면 인기 섹션에 노출하지 않는다. 1이 가장 높다. */
   popularityRank?: number;
   ```
3. `MenuService`에 `getPopularProducts(limit = 4): Promise<Product[]>`를 추가하고 정렬 책임을 컴포넌트에서 서비스로 옮긴다. 컴포넌트가 `products` 전체를 받아 자르는 지금 구조는 "메뉴 정책이 뷰에 하드코딩"된 상태다.
4. 인기 섹션은 가로 스크롤 유지. 단 스크롤 컨테이너에 `aria-label="인기 메뉴 가로 목록"`과 **끝 도달 여부를 시각/텍스트로 알리는 것**은 과하니 생략하고, 대신 마지막 카드 뒤에 "전체 메뉴 보기" 같은 걸 넣지 않는다(스크롤만으로 충분).

## 6. 전역 컴포넌트 일관성 감사

### 6.1 버튼 — `button.tsx`가 정의한 걸 호출부가 전부 덮어쓰고 있다

`components/ui/button.tsx`는 `lg` 사이즈를 `h-14 gap-2.5 px-5 text-base font-bold rounded-[16px]`로 정의한다. 그런데 실제 CTA 호출부 **8곳 전부**가 이렇게 쓴다:

```tsx
<Button size="lg" className="w-full h-14 min-h-[56px] font-extrabold text-base rounded-[16px] bg-primary text-white shadow-none hover:bg-primary/95">
```

`h-14`, `text-base`, `rounded-[16px]`는 `size="lg"`가 이미 주는 값이고, `bg-primary text-white hover:bg-primary/95`는 `variant="default"`가 이미 주는 값이다. **즉 이 className은 90%가 자기 자신을 재선언하는 노이즈다.** 이게 전형적인 AI slop 흔적이고, 실제 위험은 이거다: 나중에 `button.tsx`의 `lg`를 56px→60px로 바꿔도 **8곳이 전부 h-14로 못박아 놨기 때문에 아무 일도 안 일어난다.** 디자인 토큰이 죽어 있는 상태다.

호출부 목록: `ProductDetailSheet:317`, `CartDrawer:174`, `CheckoutSheet:216`, `ConfirmationStep:223`, `QrScannerModal:178`, `app/settings/page.tsx:317`, `app/settings/accessibility/page.tsx:95`, `app/settings/payment/page.tsx:95`, `StaffCallButton:236,244,262`.

**처방 (P1):**
1. `button.tsx`의 `default` variant에서 `shadow-none`을 빼고 `DESIGN.md`가 규정한 **파란 글로우**(`shadow-[0_4px_16px_rgba(0,100,255,0.28)]`)를 넣는다. 지금은 문서가 "primary는 blue-tinted glow shadow"라고 하는데 코드는 `shadow-none`이다 — 문서 거짓.
2. `size`에 `cta-full`을 하나 추가한다(전폭 CTA가 이 앱의 가장 흔한 형태):
   ```ts
   /** 하단 고정 액션바 전용 — 56px, 전폭 */
   "cta-full": "h-14 w-full gap-2.5 px-5 text-base font-extrabold rounded-[16px]",
   ```
3. 위 8곳의 className을 **전부 삭제**하고 `<Button size="cta-full" onClick={...}>`만 남긴다. `StaffCallButton`의 `bg-[#0064FF]`/`bg-[#F2F4F6]` 리터럴 3곳은 `variant="default"` / `variant="secondary"`로 교체.
4. `docs/component-standards.md`에 **"Button의 size/variant가 주는 값은 className으로 다시 쓰지 않는다"**를 규칙으로 명문화한다. 이게 없으면 다음 세션이 또 똑같이 쓴다.

### 6.2 포커스 링 — 레시피가 **5종**이다 (P0)

`DESIGN.md`: "**Do** give every focusable element the **same** 2px Toss Blue focus ring on `:focus-visible` — buttons, inputs, links, all identical."

실제:

| 레시피 | 위치 | 대비비(흰 배경) |
|---|---|---|
| `outline: 2px solid var(--ring); offset 2px` | `globals.css:108` 전역 | **4.92:1** ✅ |
| `focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50` + `outline-none` | **`button.tsx:9` (앱 최다 사용)** | **2.17:1** ❌ |
| `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2` + `outline-none` | ProductCard, FeaturedMenuSection, SettingsCard, LandingClientView | 4.92 ✅ |
| `focus-visible:ring-2 focus-visible:ring-primary/40 ring-offset-2` | `checkbox.tsx:21` | **1.84:1** ❌ |
| `focus-visible:ring-[3px] ring-ring/50 focus-visible:outline-1 outline-ring` | `tabs.tsx`, `badge.tsx` | 2.17 ❌ (미사용 컴포넌트) |

**핵심**: `button.tsx`의 base cva 문자열에 `outline-none`이 들어 있어서 **전역 4.92:1 아웃라인이 죽고 2.17:1 링만 남는다.** 컴파일된 CSS로 확인함(유틸리티 레이어가 base 레이어를 이김). WCAG 1.4.11(비텍스트 3:1) 미달이고, 이 제품 자체 규칙 위반이며, **키보드/스위치컨트롤 사용자가 지금 어디에 있는지 잘 안 보인다**는 실질 피해다.

**처방:**
1. `globals.css`의 전역 `:focus-visible` 아웃라인 **하나만** 진실로 삼는다.
2. `button.tsx` base에서 `outline-none focus-visible:border-ring focus-visible:ring-3 focus-visible:ring-ring/50` **전부 제거**.
3. `checkbox.tsx`의 `focus-visible:ring-2 ring-primary/40 ring-offset-2` 제거.
4. 컴포넌트 20여 곳의 `outline-none` + `focus-visible:ring-*` 조합을 전부 제거 (전역이 처리).
   - 예외: 커스텀 배경(사진/어두운 면) 위 요소는 `outline-offset`이 배경에 묻힐 수 있으니 그때만 `outline-offset: 3px` 정도로 국소 조정.
5. ESLint 커스텀 룰 또는 `docs/component-standards.md` §신설로 **"`outline-none`은 금지어"** 명문화.

그런데 `docs/component-standards.md` §2는 "**40×40px or** 44×44px"라고 쓰여 있다 — **문서끼리 충돌**하고, 코드는 작은 쪽을 골랐다.

3. 스테퍼는 전용 컴포넌트로 추출한다 → §8.1.
4. 검색 지우기 버튼(28px)은 `h-11 w-11`로 키우되 시각 원은 `after:` 의사요소로 28px 유지.

### 6.4 라운드 — 유효값 밖 + 무효 CSS 1건

`DESIGN.md`가 정한 앵커: 6 / 10 / 14 / 20 / 26 / 32 / full. `component-standards.md` §6이 "18, 22, 24 같은 중간값 손튜닝은 허용"이라고 예외를 열어 놨다. 그 예외를 감안해도:

| 값 | 사용처 수 | 판정 |
|---|---|---|
| 8px | 4곳 (`ProductCard` 품절배지, `FeaturedMenuSection` 순위칩, `checkbox` default, `settings/payment` 라디오) | ⚠️ 6과 10 사이. 배지는 `--radius-sm`(10)로 통일 권고 |
| 9px | 1곳 (`checkbox` lg) | ⚠️ 정당화 없음 |
| 12px | 6곳 | ✅ 버튼 `sm` 스케일 |
| 16px | 12곳 | ✅ 버튼 `lg` |
| 18px | 5곳 | ✅ 버튼 `cta` |
| 20/22/24/26 | 다수 | ✅ 카드/시트 |
| 28px | 1곳 (`drawer.tsx:65` `rounded-t-[28px]`) | ⚠️ 26(`--radius-xl`)이 앵커. 통일 권고 |
| **`rounded-[--radius-md]`** | 1곳 (`InvalidOrderLinkNotice.tsx:30`) | ❌ **버그** |

**`rounded-[--radius-md]` 버그 (P1, 확인 완료):** Tailwind v4.3.3에서 이 문법은 `border-radius:--radius-md`로 컴파일된다. 컴파일된 CSS에서 직접 확인했다:
```
.rounded-\[--radius-md\]{border-radius:--radius-md}
```
`var()` 래핑이 안 되므로 브라우저가 선언을 버린다 → **"샘플 매장 열기" 버튼이 직각으로 렌더된다.** `DESIGN.md`의 "never render a button under `--radius-sm` (10px)" 위반. 수정: `rounded-[14px]` (또는 v4 문법 `rounded-(--radius-md)`). **리터럴 권고** — `component-standards.md` §6이 이미 리터럴을 표준으로 정했다.

### 6.5 보더 불투명도 — §7 표준이 아직 미적용

`component-standards.md` §7이 정한 표준: `border-border`(카드) / `/40`(스티키 헤더) / `/60`(그룹 divider), `/80`은 폐기.

실제: `/80`이 **아직 살아 있다** (`StaffCallButton:135`). 추가로 `/50`(아이콘 버튼 12곳), `/15`(settings 안내 박스 2곳), `black/6`(카드 2곳)이 새로 생겼다. 표준이 4단계였는데 실제는 7단계.

**처방**: `/50` → `border-border`, `/80` → `border-border`, `black/6` → `border-border`, `/15` → `border-border/40`. 문서의 4단계 표를 그대로 강제.

### 6.6 색상 — 토큰 밖 리터럴 hex 다수 + 폐기된 브랜드 블루 부활

`app/globals.css`에 정의된 토큰이 있는데도 컴포넌트가 리터럴을 쓴다:

| 리터럴 | 대응 토큰 | 사용처 |
|---|---|---|
| `#0064FF` | `primary` | StaffCallButton×5, HeaderBar, SettingsRow, settings 2곳 |
| `#191F28` | `foreground` | ProductCard×2, FeaturedMenuSection×2, A11yToast, StaffCallButton |
| `#4E5968` | `muted-foreground` | HeaderBar, StaffCallButton |
| `#E5E8EB` | `border` | MenuCategoryHeader, StaffCallButton, switch |
| `#F2F4F6` | `muted` | MenuCategoryHeader, HeaderBar, StaffCallButton |
| `#D1D6DB` | `input` | checkbox, drawer, settings/payment |
| `#E8F2FF`/`#E8F3FF` | `accent`/`secondary` | 7곳 |
| **`#3182F6`** | **없음 — ADR 0008이 명시적으로 기각한 구 토스 블루** | `A11yToastContainer:28,99` |
| **`#5299FF`** | 없음 | `A11yToastContainer:99` |

**가장 심각한 건 `#3182F6`**이다. ADR 0008이 "`#0064FF` canonical — resolved over the brand-guide's `#3182f6`"라고 결론 내렸는데, 토스트의 성공 아이콘과 "취소" 링크가 그 폐기된 값을 쓰고 있다. **결정된 ADR이 코드에서 되살아난 상태**다.

**처방:**
1. **리터럴 hex가 컴포넌트에 남는 유일한 정당한 사유는 "토큰이 없는 값"이다.** 토큰이 있는 것(위 표 상단 7종)은 전부 유틸리티 클래스로 교체 — 기계적 작업이고 고대비 모드 대응이 자동으로 따라온다.
2. 토큰이 없는 것(`#3182F6`, `#F04452`, 토스트 아이콘 4색, success 2색)은 **globals.css에 토큰을 신설하거나 기존 토큰으로 흡수한다.** 구체적으로:
   - `#3182F6` / `#5299FF` → `primary` / `primary/80`로 흡수, 삭제.
   - `#F04452` + `#FEEBE8` → `--destructive`(`#B91C1C`) + `bg-destructive/10`으로 흡수. 현재 3.23:1 → 5.46:1로 개선(§7.1).
   - success → `--success: #00A85A` / `--success-bg: #E8F8EE`를 `@theme`에 신설하되, **`DESIGN.md`의 Status-Color Exception Rule대로 텍스트로는 쓰지 않는다**(아이콘/큰 면적 전용). 지금 12px 텍스트로 쓰고 있어서 2.83:1 실패 중.
   - 토스트 아이콘 4색 → §8.2의 `ToastItem.variant` 도입 시 토큰 매핑으로 해소.
3. `globals.css`에서 `.high-contrast`가 `--destructive`를 재정의하지 않는 건 문서상 의도된 것(6.47:1이면 충분) — **유지.**

### 6.7 체크박스 / 스위치 / 설정 피드백

- `Checkbox`는 3사이즈(20/24/28px)를 제공하지만 **호출부 8곳 전부 default(24px)만 쓴다.** `sm`/`lg`는 죽은 분기다. → 사이즈 prop을 지우거나, 24px가 44px 히트영역을 못 채우므로 **`SettingsRow` 전체가 `<label htmlFor>`로 클릭 가능**한 현재 구조를 문서화하고 사이즈 prop을 제거하는 게 낫다(실제 타깃은 64px 행이다 — 이 처리는 **잘 되어 있다**).
- `Switch`는 **어디서도 안 쓴다.** ADR 0012 §6이 "Switch를 토스 표준 50×30px로 업그레이드했다"고 기록해 놨는데 그 컴포넌트는 설정에서 Checkbox로 교체되면서 고아가 됐다. → 삭제 또는 ADR에 사후 기록.
- **`/settings` 3개 페이지에서 시각 토스트가 절대 안 뜬다 (P0).** `notify()`는 `ToastItem`을 **반환만** 하고 스토어에 넣지 않는다. 설정 페이지 6개 호출부가 전부 반환값을 버린다. 게다가 `<A11yToastContainer />`는 `MenuClientView` 안에만 마운트되어 있어서 설정 라우트에는 토스트 UI 자체가 없다.
  - 결과: **스크린리더 사용자는 "고대비 모드 설정이 켜졌습니다"를 듣지만, 시각 사용자는 아무 확인도 못 받는다.** 접근성 제품에서 시각 사용자만 정보가 부족한 역전 현상.
  - 추가로 `handleComplete()`는 `notify(...)` 직후 `router.back()`을 호출한다 — 라이브 리전이 낭독을 마치기 전에 화면이 바뀐다.
  - 처방은 §8.2.

### 6.8 헤더 / 스크롤 동기화 (P1)

현재(타 세션 변경 반영): `HeaderBar` = `sticky top-0 h-[58px]`, `MenuCategoryHeader` = `sticky top-[58px] py-2.5` (≈60px) → **누적 고정 크롬 118px**. 섹션은 `scroll-mt-[116px]`, 프로그래매틱 스크롤 오프셋은 `-114`.

그런데 스크롤스파이는 그대로다:
```ts
// MenuClientView.tsx:80
const headerThreshold = 100;
if (rect.top <= headerThreshold) matchedCategory = cat.id;
```
카테고리 X를 탭하면 X의 `rect.top`이 약 **114~116px**에 놓인다. 114 > 100이므로 스파이는 X를 매치하지 않고 **직전 카테고리를 활성으로 유지**한다. `isProgrammaticScroll`이 500ms 막아주지만, 그 후 손가락이 1px만 움직여도 활성 pill이 **이전 카테고리로 되돌아간다.**

**처방:**
1. 매직넘버 3개(`100`, `114`, `116`)를 하나의 상수로 통합:
   ```ts
   // components/flow/menuLayout.ts (신규, 상수 전용)
   export const HEADER_H = 58;
   export const CATEGORY_BAR_H = 60;
   export const STICKY_CHROME_H = HEADER_H + CATEGORY_BAR_H; // 118
   export const SCROLLSPY_THRESHOLD = STICKY_CHROME_H + 8;   // 126 — 크롬 바로 아래
   ```
2. `scroll-mt`는 인라인 스타일 `style={{ scrollMarginTop: STICKY_CHROME_H }}`로 바꿔 클래스 리터럴과 상수가 갈라지지 않게 한다.
3. **더 나은 안**: 고정 상수 대신 `MenuCategoryHeader`에 `ref`를 달아 `getBoundingClientRect().bottom`을 실측한다. fontScale 1.3에서는 카테고리 pill 높이가 실제로 커지므로 **고정 118px은 큰 글씨 사용자에게 틀린 값**이다. 이 제품에서는 실측이 정답이다.
4. `handleScroll`이 `window`의 scroll마다 **8개 카테고리 전부에 `getBoundingClientRect()`를 호출**한다(강제 레이아웃 8회/프레임). Lenis가 켜져 있으면 60fps로 돈다. → `IntersectionObserver`로 되돌리되, `docs/ux-audit.md` §2.1이 지적한 "여러 entry 중 마지막이 이김" 버그를 피하기 위해 **`intersectionRatio` 최대값 하나만 채택 + 값이 같으면 setState 생략**으로 구현한다.

### 6.9 헤더 뒤로가기 목적지 버그

```tsx
// HeaderBar.tsx:18-19
const pathname = usePathname();
const backHref = pathname || `/order/${storeInfo.storeId}`;
```
`usePathname()`은 쿼리스트링을 뺀 **현재 경로**를 준다. `/order/jumun-cafe-01?table=3`에서 뒤로가기를 누르면 `/order/jumun-cafe-01`로 이동 → **테이블을 이미 아는 QR 사용자에게 "매장 식사/포장" 선택 화면이 다시 뜬다.** "뒤로"의 의미가 "한 단계 되감기"가 아니라 "진입 플로우 처음으로"가 됐다.

**처방**: 이 화면은 플로우의 **시작점**이다(QR 진입 시). 뒤로가기 버튼을 조건부로 처리:
- `?table=`/`?type=`으로 직접 진입(QR/NFC) → 뒤로가기 대신 **설정 아이콘**을 놓거나 버튼을 아예 렌더하지 않는다. 갈 곳이 없는 뒤로가기는 사용자를 혼란시킨다.
- 수동 선택으로 도달 → `/order/[storeId]` (선택 화면)로. 이건 지금 동작과 같다.
- 판별은 서버 컴포넌트(`app/order/[storeId]/page.tsx`)가 이미 `tableValue`/`typeValue`를 알고 있으므로 `<HeaderBar backHref={...} />`로 **prop 주입**하면 된다. 클라이언트에서 `usePathname()`으로 추측하지 않는다.

### 6.10 "새로운 주문하기"가 테이블 컨텍스트를 잃는다

```tsx
// ConfirmationStep.tsx:110-118
router.push(`/order/${storeId}`);   // table/type 없음
```
매장 식사 주문을 마친 사용자가 "새로운 주문하기"를 누르면 **다시 매장식사/포장을 고르고 테이블 번호를 다시 찍어야 한다.** `lastReceipt.store`에 `orderType`과 `table`이 다 들어 있다.

**처방:**
```ts
const { store } = lastReceipt;
const href = store.orderType === "dine-in"
  ? `/order/${store.storeId}?table=${store.table}`
  : `/order/${store.storeId}?type=takeout`;
```
단, `onReset()`이 `storeInfo: null`로 지우므로 **href를 먼저 계산한 뒤 reset**해야 한다(현재 코드는 storeId만 먼저 뽑아서 우연히 동작 중).

### 7.2 16px 텍스트 하한선 — **재위반**

`docs/ux-planning-2026-08.md` §5가 "29곳을 전부 `text-base`로 고쳤다. **Resolved**"라고 기록해 뒀고, ADR 0012는 "Zero sub-16px text ... remain across the entire codebase"라고 단언한다. **둘 다 지금은 거짓이다.**

| 클래스 | px | 개수 | 위치 |
|---|---|---|---|
| `text-[11px]` | 11 | 2 | `HeaderBar:55,62` (감사 중 타 세션이 **새로 추가**) |
| `text-xs` | 12 | 8 | `StaffCallButton:181,204`, `ConfirmationStep:148`, `LandingClientView:99,156,160,168`, `HeaderBar:55,62`(sm:) |
| `text-sm` | 14 | 12 | `StaffCallButton:213`, `LandingClientView:55,68`, `ProductDetailSheet:249`, `CartSummaryPill:67`, `FeaturedMenuSection:97`, `ConfirmationStep:148,163,173,187,192`, `HeaderBar:43` |
| `text-[15px]` | 15 | 5 | `ProductCard:80`, `FeaturedMenuSection:109`, `LandingClientView:96,153`, `CartSummaryPill:71`, `HeaderBar:49` |

**총 27곳.** `sm:text-*`로 데스크톱에서만 커지는 패턴이 여럿인데, 이 제품의 실제 타깃 뷰포트는 360~430px이므로 **`sm:` 업그레이드는 아무도 못 본다.**

**결정이 필요한 지점** (`ux-planning-2026-08.md` §5가 제기했다가 "전부 16px로 수정"으로 닫았지만 되돌아왔으므로 **한 번 더 확정해야 한다**):

- **안 A — 절대 16px 유지 (현행 문서 그대로).** 배지·타임스탬프까지 전부 16px. 시각적 위계가 평평해지고 배지 패딩·행 높이를 다시 조정해야 한다. 하지만 문서 3곳이 "예외 없음"이라고 못박은 값이다.
- **안 B — 범위 한정 재정의.** "사용자가 **과업을 완료하기 위해 읽어야 하는 텍스트**(메뉴명, 가격, 옵션명, 폼 라벨, 본문, 버튼 라벨)는 16px 하한. **정보 중복이거나 장식적인 메타**(이미 접근명에 포함된 배지 텍스트, 순위 칩)는 14px 하한, 11~13px 금지." — 이 정의라면 `HeaderBar`의 테이블 pill은 헤더 `aria-label`에 이미 들어 있으므로 14px 허용, `ProductCard` 메뉴명 15px는 **여전히 위반**.
- **권고: 안 B.** 단, 안 B를 택하려면 **`DESIGN.md` / `docs/design-system.md` / ADR 0012 세 문서를 동시에 개정**해야 하고, 새 규칙을 "왜 이게 여전히 접근성 하한선인가"와 함께 ADR로 남겨야 한다. 안 B를 택해도 위 27곳 중 **최소 12곳은 여전히 고쳐야 한다**(메뉴명·가격·설명·CTA 라벨 계열).
- 어느 쪽이든 **fontScale이 곱해진다**는 점을 문서에 명시할 것: 11px × 1.3 = 14.3px로 여전히 작다.

## 8. AI slop / 유지보수 부채 — 구체 처방

여기가 "지금은 안 아프지만 6개월 뒤 지옥이 되는" 항목들이다. 각각 **무엇을 어느 파일로 어떻게 쪼개거나 합칠지**까지 적었다.

### 8.1 `ProductCard`와 `FeaturedMenuSection`의 카드 마크업 완전 복제 (최우선)

`FeaturedMenuSection.tsx:76-116`은 `ProductCard.tsx:34-90`의 **거의 문자 그대로의 복사본**이다. 동일한 것: `themeBg` fallback, `aspect-[4/5] sm:aspect-[1/1]`, `rounded-[22px]`, `border-black/6 dark:border-white/10`, `shadow-resting`, `group-hover:scale-106`, 유리 패널 전체(마스크·틴트·blur), `text-[15px]`/`text-base` 타이포, `#191F28` 리터럴, `tracking-[0.6px]`.

즉 **§3의 카드 재설계를 하면 같은 수정을 두 번 해야 하고, 한 번 빠뜨리면 즉시 갈라진다.** 실제로 이미 갈라져 있다: `ProductCard`는 `min-h-[190px]`인데 `FeaturedMenuSection`은 `min-h-[185px]`, 품절 처리도 `ProductCard`에만 있다(캐러셀은 `disabled`만 걸고 회색조·배지가 없다 — **인기 메뉴가 품절이면 아무 표시가 없다**).

**처방:**
```
components/flow/ProductCard.tsx   ← 단일 소스. layout: "grid" | "row" | "carousel"
components/flow/FeaturedMenuSection.tsx  ← <ProductCard layout="carousel" rank={i+1} /> 만 렌더
```
`FeaturedMenuSection`은 **섹션 헤더 + 가로 스크롤 컨테이너 + 데이터 선별**만 책임진다(76~116줄 삭제). 순위 칩은 `ProductCard`의 `rank?: number` prop으로.

이렇게 하면 §3의 재설계가 **한 파일 수정으로 세 화면에 전파**된다.

### 8.2 `notify()` API가 호출자에게 "스토어에 넣기"를 기억시킨다 (설계 결함)

```ts
export function notify(kind, messageKo, options): ToastItem   // 반환만 함
```
호출부 8곳 중:
- `useCartStore` 3곳: 반환값을 `set({toasts: [...]})`에 넣음 ✅
- `StaffCallButton` 1곳: `useCartStore.setState(...)`를 **직접** 호출 (스토어 액션 우회) ⚠️
- `app/settings/*` 6곳: **반환값을 버림** ❌ → §6.7의 P0

이건 "잘못 쓰기 쉬운 API"의 교과서적 사례다. 실제로 6/10이 잘못 쓰고 있다.

**처방 — 책임을 함수 이름으로 분리한다:**

```ts
// lib/services/A11yFeedbackService.ts
/** 스크린리더 라이브 리전에만 알린다. 시각 UI 없음. */
export function announce(messageKo: string, priority?: "polite" | "assertive"): void

/** 라이브 리전 + 햅틱 + 시각 토스트까지 전부 처리한다. 반환값 없음. */
export function toast(input: {
  kind: "success" | "error";
  messageKo: string;
  variant?: ToastVariant;      // 아이콘 결정용 — §6.11의 문자열 매칭 제거
  onUndo?: () => void;
}): void
```
`toast()`가 내부에서 `useCartStore.getState().pushToast(...)`를 호출한다. 순환 참조는 없다(현재 주석이 확인한 대로 `A11yFeedbackService`는 스토어를 import하지 않지만, `getState()` 접근은 런타임 참조라 안전하다. 걱정되면 `useToastStore`를 별도로 분리한다 — **오히려 이게 더 낫다**: 토스트가 `useCartStore`에 얹혀 있는 것 자체가 응집도 문제다).

**추가 처방 — 토스트를 카트 스토어에서 분리:**
```
store/useToastStore.ts   ← toasts[], pushToast, dismissToast  (신규)
store/useCartStore.ts    ← 카트 상태만. toasts/showToast 제거
```
현재 `/settings`에서 토스트를 띄우려면 **장바구니 스토어를 건드려야 하는** 이상한 구조다. 분리하면 `<A11yToastContainer />`를 `app/layout.tsx`에 한 번만 마운트해서 전 라우트에서 동작시킬 수 있다 (§6.7 해결).

### 8.3 하단 고정 액션바가 6곳에 복붙되어 있다

이 문자열이 **글자 하나 안 틀리고** 6개 파일에 있다:
```
absolute/fixed bottom-0 left-0 right-0 z-30/z-40 pointer-events-none flex justify-center
  → w-full pointer-events-auto flex flex-col pt-7 px-4 pb-[calc(1rem+env(safe-area-inset-bottom,0px))]
    bg-gradient-to-t from-background via-background/95 to-transparent backdrop-blur-[6px]
    [mask-image:linear-gradient(to_top,black_80%,transparent_100%)]
    [-webkit-mask-image:linear-gradient(to_top,black_80%,transparent_100%)]
```
위치: `ProductDetailSheet:313`, `CartDrawer:169`, `CheckoutSheet:211`, `ConfirmationStep:219`, `app/settings/page.tsx:312`, `settings/accessibility:90`, `settings/payment:90`. (7곳)

이미 갈라진 부분: `z-30` vs `z-40`, `absolute` vs `fixed` vs `sticky`, `pb-[calc(1rem+…)]` vs `pb-[calc(0.875rem+…)]`, settings만 `max-w-[768px]` 추가.

**처방 — 신규 컴포넌트 1개:**
```tsx
// components/layout/StickyActionBar.tsx
interface StickyActionBarProps {
  children: React.ReactNode;
  /** 드로어 내부(absolute) vs 라우트 레벨(fixed). 기본 "fixed" */
  position?: "fixed" | "absolute";
  className?: string;
}
```
`safe-area-inset`, 그라데이션, 마스크, z-index, max-width를 **한 곳에서만** 정의. 7곳이 `<StickyActionBar><Button size="cta-full">…</Button></StickyActionBar>`로 줄어든다.

이건 `docs/design-system.md`의 "safe-area-inset 처리는 선택이 아니다" 요구를 **구조적으로 보장**하는 방법이기도 하다 — 지금은 새 화면을 만들 때 개발자가 그 긴 문자열을 기억해서 복붙해야 한다.

### 8.4 뒤로가기 아이콘 버튼이 12곳에 복붙되어 있다

```tsx
<motion.div whileTap={reduceMotion ? undefined : {scale:0.90}} transition={{type:"spring",stiffness:400,damping:25}}>
  <Button variant="ghost" size="icon" className="h-10 w-10 rounded-full bg-background/85 hover:bg-background text-foreground backdrop-blur-md shadow-sm border border-border/50 flex items-center justify-center -ml-1">
    <ChevronLeft className="size-6 stroke-[2.5]" aria-hidden="true" />

```
12곳. 이미 갈라짐: `shadow-sm` vs `shadow-2xs` vs `shadow-xs`, `-ml-1` 유무, `asChild`+`Link` vs `onClick`.

**처방:**
```tsx
// components/layout/BackButton.tsx
interface BackButtonProps {
  /** 링크로 이동. onClick과 상호배타 */
```

### 8.5 수량 스테퍼가 2곳에 다른 크기로 복붙

`ProductDetailSheet:202-230`(36px)과 `CartDrawer:126-152`(32px). 로직도 다르다 — 상세는 `setQuantity(q => clamp)` 로컬 상태, 카트는 `updateQuantity(id, delta)` 스토어 액션.

**처방:**
```tsx
// components/ui/QuantityStepper.tsx
interface QuantityStepperProps {
  value: number;
  onChange: (next: number) => void;
  min?: number;      // 기본 1
  max?: number;      // 기본 20
  /** SR 라벨 접두사. 예: "아메리카노" → "아메리카노 수량 1개 늘리기" */

  size?: "default";  // 44px 단일 — §6.3
```

카트는 `onChange={(n) => setQuantity(item.id, n)}`로 쓰고, `useCartStore`에 델타 기반 `updateQuantity` 대신 **절대값 기반 `setQuantity(id, n)`**를 추가한다(델타 API는 호출부가 현재 값을 알아야 해서 경합에 취약하다).

### 8.8 `MenuService`의 N+1 호출 패턴

```tsx
// app/order/[storeId]/page.tsx:37-42
const categories = await MenuService.getCategories();           // +200ms
const productsNested = await Promise.all(
  categories.map((cat) => MenuService.getProductsByCategory(cat.id))  // 8회 × 200ms (병렬)
);
```
직렬 2단계라 **최소 400ms의 인위 지연**이 모든 메뉴 페이지 진입에 붙는다. 그동안 §7.3.8대로 로딩 UI가 없어 빈 화면이다.

**처방:**
1. `MenuService.getMenu(): Promise<{ categories: MenuCategory[]; products: Product[] }>` 하나로 통합. 호출 1회, 200ms.
2. `MOCK_LATENCY_MS`를 `0`으로 두거나 env 플래그(`NEXT_PUBLIC_MOCK_LATENCY`)로 뺀다. 실 백엔드가 없는 지금 400ms는 **순수 손해**다. 로딩 상태 검증용으로 켜고 싶으면 플래그로.

## 10. 데이터 · 서비스 · 타입 레이어

### 10.1 `menu.json` 상태

18개 상품 / 8개 카테고리 / 옵션그룹 4종(`temperature`, `size`, `milk`, `syrup`). 품절 1개(`chocolate-brownie`) — 이건 감사 시점에 잘 시드되어 있다 ✅.

문제:
- `lib/types/menu.ts:1-11`의 `ProductCategory` 유니온에 **`brunch`가 남아 있다** — 방금 `menu.json`에서 제거된 카테고리. `(string & {})` 때문에 타입 에러가 안 난다.
- `(string & {})` 트릭 자체가 문제다. **카테고리 id 오타가 타입 에러가 아니라 런타임 빈 섹션으로 나타난다.** `MenuClientView:187`이 `categoryProducts.length === 0`이면 `return null`하므로 **조용히 사라진다.**
  - **처방**: `menu.json`을 단일 진실로 삼고 `ProductCategory`를 유니온 리터럴로 좁히거나, 아예 `string`으로 두고 **런타임 검증**을 넣는다. 후자를 권고:
    ```ts
    // MenuService 모듈 로드 시 1회
    const knownCategoryIds = new Set(CATEGORIES.map(c => c.id));
    const orphans = PRODUCTS.filter(p => !knownCategoryIds.has(p.category));
    if (orphans.length && process.env.NODE_ENV !== "production") {
      console.warn(`[MenuService] 알 수 없는 카테고리를 가진 상품: ${orphans.map(p=>p.id).join(", ")}`);
    }
    ```
- `MenuService.tsx:11-13`의 `RawProduct`가 `Omit<Product,"optionGroups"> & { optionGroupIds: string[] }`인데, **`menuData`는 `as RawProduct[]`로 단언될 뿐 검증되지 않는다.** `optionGroupIds`에 없는 id가 들어가면 `OPTION_GROUPS[id]`가 `undefined`가 되고 `product.optionGroups`에 `undefined`가 섞여 **`ProductDetailSheet`가 런타임에 터진다.**
  - **처방**: 매핑 시 `.filter(Boolean)` + 개발 모드 경고. 또는 `menu.json`용 타입을 `lib/types/menu.ts`에 `MenuDataFile`로 명시하고 `as` 단언 대신 `satisfies`를 쓴다.
- `menu.json`에 `git diff` 결과 **빈 줄 하나**가 남아 있다(brunch 상품 제거 흔적). 포매팅 정리 필요.
- **가격 타입**: 전부 `number` KRW. `toLocaleString("ko-KR")`이 8곳에 흩어져 있다 → `lib/format.ts`에 `formatKRW(n: number): string`로 통일 권고 (지금은 `tabular-nums tracking-[0.6px]` 클래스도 함께 복붙되고 있다).

```ts
export interface Product {
```

### 10.3 검색 개선 (`es-hangul` 배선)

```ts
// components/flow/MenuSearchSection.tsx
import { getChoseong } from "es-hangul";

const categoryLabel = new Map(categories.map(c => [c.id, c.labelKo]));  // ← props로 받아야 함
const q = trimmedQuery;
const qChoseong = getChoseong(q);

const match = (p: Product) =>
  p.nameKo.includes(q) ||
  getChoseong(p.nameKo).includes(qChoseong) ||   // "ㅇㅁㄹㅋㄴ" → 아메리카노
  p.descriptionKo.includes(q) ||
  (categoryLabel.get(p.category) ?? "").includes(q);  // ← "커피" 검색 동작 (§6.11)
```
`MenuSearchSection`이 지금 `categories`를 안 받으므로 **prop 추가 필요**. `MenuClientView`가 이미 갖고 있다.
`es-toolkit`의 `debounce`는 이 규모(18개)에서는 불필요하다 — **`es-toolkit`은 지우는 게 정직하다.**

### 10.4 `OrderService`의 랜덤 실패

`MOCK_FAILURE_RATE = 0.1` — **10% 확률로 결제가 실패한다.** 데모/QA 중 10번에 1번 결제가 깨진다. `forceFailure` 옵션이 이미 있으니 기본 실패율은 **0으로 두고** `?debug=fail` 같은 명시적 트리거로 바꾸는 게 맞다. `docs/testing-strategy.md`가 요구한 "실패 경로가 도달 가능함"은 `forceFailure` 테스트가 이미 증명한다.

### 10.5 `removeItem` undo가 순서를 잃는다

```ts
onUndo: () => set({ items: [...get().items, removed] })   // 항상 맨 뒤에 붙음
```
3개 중 1번째를 지우고 되돌리면 **3번째 자리로 간다.** 인덱스를 캡처해서 `splice` 복원 권고.

1. `docs/ux-audit.md`는 **완료된 과거 감사**다. 상단에 "이 문서의 모든 항목은 해결됨. 역사적 기록으로만 보존" 배너를 달거나 `docs/archive/`로 이동.
2. ADR 0012는 **수치가 거의 다 틀렸다.** ADR은 "그때의 결정"이므로 사후 수정 대신 **Superseded 표시 + 후속 ADR**이 맞다. 새 ADR(0015)에 §3의 카드 재설계 결정과 실제 수치를 기록.
3. `component-standards.md`는 **규범 문서**이므로 코드와 맞춰 갱신해야 한다. 단 §6.3처럼 **문서끼리 충돌**하는 건 상위 문서(`design-system.md`) 기준으로 통일.
4. `project-status-and-roadmap.md`의 "100% 동기화" 문장은 삭제. 이런 문장이 남아 있으면 다음 세션이 문서를 검증 없이 신뢰한다.

### 3번·5번 "보류"의 실행상 의미

- `components/flow/QrScannerModal.tsx` — **내용(카메라 로직, 카피, 라우팅) 무변경.** §15의 폴더 재구성(파일 위치 이동)에는 포함시키되, 로직·문구·배선 여부는 손대지 않는다. `docs/features.md`·`component-standards.md`가 이 컴포넌트를 "살아 있다"고 서술하는 부분은 §14의 문서 동기화 때 "코드에는 존재하나 어떤 화면에서도 진입 경로가 연결되어 있지 않음"으로 **정정만 하고, 연결 여부 자체는 건드리지 않는다.**
- 언어 설정 — `app/settings/page.tsx`의 `LANGUAGES` 배열·언어 피커 UI, `useAccessibilityStore`의 `language`/`setLanguage`, `lib/types/accessibility.ts`의 `AppLanguage`, `AccessibilityService`의 `language` 필드 — **전부 무변경.** §7.3.5("아무 동작도 안 하면서 낭독은 한다")는 이번 라운드의 이슈 목록에서 제외한다.
- 두 항목 다음 라운드에서 별도로 다시 논의한다 — 이 문서를 그때 갱신할 것.

### 4번 상세 설계 — `applyPreset` 퀵 프리셋 UI

`useAccessibilityStore.applyPreset("visual"|"hearing"|"reading"|"senior")`는 이미 구현되어 있고 테스트도 있다(§9.1). UI만 없다.

- **위치**: `app/settings/page.tsx`, "화면 및 텍스트 상세 설정" 섹션 **위**에 새 섹션 "빠른 설정"을 추가한다. 이 페이지에 처음 들어온 사용자가 가장 먼저 보는 자리 — 개별 토글을 하나씩 만지기 전에 자기 상황에 맞는 묶음을 고를 수 있게.
- **형태**: `SettingsCard` 4장을 `grid-cols-2` 2×2로. 각 카드는 `onClick`만 있고 `href`/`isSelected` 없음(프리셋은 지속 선택 상태가 아니라 일회성 액션이므로 라디오처럼 취급하지 않는다).
- **레이블 4종** (제품 타깃 문구, `PRODUCT.md` 원칙에 맞춰 장애 카테고리명을 그대로 노출하지 않고 상황 중심으로 표현):
  - `visual` → "또렷하게 보기" / 설명 "고대비, 큰 글씨, 알림 오래 표시"
  - `hearing` → "진동으로 확인하기" / 설명 "진동 피드백, 알림 오래 표시"
  - `reading` → "편하게 읽기" / 설명 "간격 넓히기, 애니메이션 줄이기"
  - `senior` → "크고 안정적으로" / 설명 "큰 글씨, 진동 피드백, 알림 오래 표시"
- **아이콘**: lucide-react 카탈로그에서 각 문구에 맞는 아웃라인 아이콘 선정(정확한 export명은 구현 시 확인 — 후보: 대비/확대류, 진동류, 책/줄간격류, 사람류).
- **클릭 시**: `applyPreset(id)` 호출 + 바뀐 항목을 요약한 문장으로 `toast()`(§3단계에서 나올 새 API) 호출. `applyPreset` 자체는 diff를 반환하지 않으므로 **프리셋별 요약 문구를 호출부에 하드코딩**한다 — 예: `"또렷하게 보기 설정이 적용되었어요 (고대비, 글자 크게, 알림 표시 시간 연장)"`.
- **주의할 구현 함정**: `SettingsCard`의 트레일링 아이콘은 `trailing ?? <ChevronRight />`로 되어 있다 — `??`는 `null`도 nullish로 취급해 대체하므로 **`trailing={null}`을 넘겨도 여전히 ChevronRight가 뜬다.** 네비게이션이 아닌 액션 카드이므로 셰브런은 오해를 준다. `trailing={<span className="sr-only">적용</span>}`처럼 빈 시각 요소를 명시적으로 넘겨야 진짜로 숨는다.

### import 경로 영향

파일 이동은 **한 커밋으로 몰아서, 기능 변경과 섞지 않는다.** 순서: (1) `git mv`로 파일 이동 (2) 프로젝트 전체에서 옛 경로를 새 경로로 일괄 치환 (3) `tsc --noEmit` + `vitest run` + `next build` 3종 세트로 누락 확인 (4) 그 커밋만 별도로 만든다. 기능 수정과 같은 커밋에 섞으면 diff가 커져서 리뷰가 불가능해진다.

## 16. 메뉴 화면 헤더 레이아웃 결정 — 매장/포장 텍스트 위치 + 설정 버튼

### 현재 상태 (타 세션이 편집 중인 최신 버전 기준)

```
grid-cols-[40px_1fr_40px], h-[58px]
좌: 40px 뒤로가기 (§6.3 — 44px 미달)
중: 2단 — <h1>매장명</h1> + <span>테이블/포장 배지</span> (text-[11px] — §7.2 위반, 감사 중 새로 생김)
우: 빈 40px 스페이서 — 설정 버튼 없음
```

### 요구사항 (문서 근거)

- `PRODUCT.md`: "A small settings icon (44px+ target, top corner) ... [is an] only persistent affordance"
- ADR 0003: "A small settings-icon affordance is present throughout ... a single icon, not a tab bar" — **"throughout"**, 예외 없음
- 그런데 실제로는 랜딩·주문유형선택·테이블선택 3화면엔 설정 아이콘이 있고, **정작 가장 오래 머무는 메뉴 화면(HeaderBar)에만 없다.**

### 옵션 비교

| | A. 현행 유지 | **B. 2단 중앙 + 우측 설정 버튼** | C. 1단 압축 + 배지를 카테고리헤더로 이동 | D. 배지 제거 |
|---|---|---|---|---|
| ADR0003 "throughout" 충족 | ❌ | ✅ | ✅ | ✅ |
| 테이블 번호 상시 노출(인지부하 경감) | ✅ | ✅ | ⚠️ 스크롤 후 카테고리헤더에 묻힘 | ❌ |
| 헤더 높이 | 58px | 58px(변경 없음) | ~48px | ~48px |
| 구현 범위 | — | 우측 슬롯 1개 교체 | 헤더+카테고리헤더 동시 재작업 | 헤더 단순화, 정보 손실 |
| 타 세션 작업과의 충돌 | — | 최소(이미 만든 2단 구조 유지) | 큼 | 중간 |

### 결정: **B**

최소 변경으로 표준 요구사항을 채우고, 타 세션이 이미 만든 2단 구조를 재작업하지 않는다. 테이블 번호 상시 노출은 이 제품의 실제 타깃(고령자·인지부하 사용자)에게 실질적 이득이라 굳이 없앨 이유가 없다.

### 확정 스펙

```
grid-cols-[44px_1fr_44px]                 ← 40→44 통일 (§6.3)
좌: <BackButton href={backHref} />         ← §15 shared 컴포넌트. backHref는 서버(app/order/[storeId]/page.tsx)가
                                              계산해 prop으로 내려준다 — usePathname() 추측 금지 (§6.9 버그 수정)
중: <h1>{storeName}</h1>                    ← 페이지 유일 h1로 유지, 정상 낭독(요약 타이틀 역할)
    <span aria-hidden="true"
          className="text-sm">              ← 14px. §7.2 안B 근거: 완전한 문장이 이미 header의
      {테이블/포장 배지}                       aria-label에 있으므로 이 배지는 "중복·장식 메타"로 분류된다
    </span>
우: <SettingsIconButton />                  ← §15 shared 컴포넌트, size-11(44px), aria-label="설정 열기"
header: aria-label={`${storeName}, ${orderTypeLabel}`}   ← 이미 있음, 올바르므로 유지
```

**부수 효과**: `SettingsIconButton`을 새로 만들면서 이미 있던 3곳(Landing/OrderTypeSelect/TableSelect)의 40px 버튼도 같은 컴포넌트로 교체 — 4곳의 크기 불일치가 한 번에 해소된다(§6.3).



## 17. 실행 플레이북 — 파트 1: 단계 요약

각 단계는 **독립적으로 커밋 가능**하고, 앞 단계가 뒤 단계의 전제다. 각 항목의 정확한 파일·순서·"어떻게"는 §18(파트 2)에 있다 — 이 섹션은 훑어보기용 목차다.

### 0단계 — 착수 전 (필수, 갱신됨)
- **타 세션이 계속 편집 중이다.** 이 문서 작성 시작 시점엔 파일 1개(`menu.json`)가 수정 상태였는데, 지금은 8개(`CartSummaryPill`, `MenuCategoryHeader`, `MenuClientView`, `MenuSearchSection`, `StaffCallButton`, `HeaderBar`, `menu.json`, `components.test.tsx`)로 늘었다. 실행 착수 전 `git status`/`git diff`로 다시 확인하고, 가능하면 그 세션이 매듭지어질 때까지 기다리거나 직접 조율한다.
- **16px 하한선(§7.2)은 이제 결정 완료(§13, 안 B)** — 더 이상 막는 결정이 아니다. 다만 착수 직전에 `text-xs`/`text-sm`/`text-\[1[0-5]px\]` 전수 grep을 한 번 더 돌려라 — 이 감사 도중 타 세션이 `HeaderBar`에 `text-[11px]`를 새로 추가한 걸 확인했다. 목록이 다시 늘어나 있을 가능성이 높다.
- §13에서 3번·5번은 보류로 확정됐다 — 아래 1~10단계 어디에도 그 두 항목에 대한 실제 코드 변경은 없다(있다면 오류).
