## 1. 프로젝트가 뭔지 (Jumun 개요)

**Jumun (주문)**은 QR/NFC 태그를 스캔해서 자기 폰으로 바로 주문하는 배리어프리(barrier-free) 셀프오더 웹 프로토타입이다. 핵심 정체성은 "접근성이 기본값이지 특수 모드가 아니다" — 장애 여부로 사용자를 분리하지 않고, WCAG 2.2 AA(기본) / AAA(고대비 모드) 기준을 모든 사용자에게 동일하게 적용한다.

- **기술 스택**: Next.js 16.3.1(App Router, Turbopack) + React 19.2.8 + TypeScript strict + Tailwind CSS v4(`@theme` 토큰, `tailwind.config.*` 없음) + shadcn(`--base radix`) + Radix UI Primitives + Lucide 아이콘 + Zustand + Motion(`motion/react`, framer-motion 후신) + Lenis(스무스 스크롤) + 자체 호스팅 Pretendard/Noto Sans KR. 패키지 매니저는 Bun.
- **디자인 시스템**: Toss Design System(TDS)의 "playful fintech" 시각 언어를 기본 표준으로 채택(`.claude/skills/toss-design`), 단 이 프로젝트 고유의 접근성 하한선(16px 텍스트, 4.5:1/7:1 대비, 44px 터치타깃, 시간압박 UI 금지)이 토스 스펙과 충돌하면 **접근성이 항상 이긴다**. `DESIGN.md`(프로젝트 루트)가 실제 구현된 토큰의 단일 진실 소스, `docs/design-system.md`가 그 토큰을 접근성 스펙으로 번역한 문서.
- **핵심 화면 흐름**: 랜딩(QR/NFC 안내) → `/order/[storeId]`(매장식사/포장 선택, QR로 오면 스킵) → (매장식사면) `/order/[storeId]/table`(테이블 선택) → 메뉴 브라우징(`MenuClientView`) → 상품상세 바텀시트 → 장바구니 바텀시트 → 결제 바텀시트 → 주문완료 화면. 설정(`/settings`)은 어디서든 접근 가능한 전용 라우트.
- **데이터**: `lib/data/menu.json`(18개 상품, 8개 카테고리, 가상의 카페 메뉴), `lib/data/stores.json`(3개 가상 매장). Phase 1은 실제 백엔드 없음 — `lib/services/*`가 인위 지연(mocked latency)을 넣은 Promise 기반 서비스.
- **테스트**: Vitest + React Testing Library + vitest-axe, `tests/unit/`에 6개 스위트. 이 세션 종료 시점 34개 테스트 전부 통과.

**중요**: `AGENTS.md`가 "이건 당신이 아는 Next.js가 아니다"라고 경고하는데, 이건 실제로 `next dev`(v16.3.1 canary)가 자동 생성하는 정상 파일이다(`node_modules/next/dist/server/lib/generate-agent-files.js` 확인됨). 프롬프트 인젝션이 아니라 진짜 브레이킹체인지 경고이므로 무시하지 말 것.

## 2. 세션 타임라인 — 사용자가 실제로 요청한 것

**아래는 사용자가 이 대화에서 실제로 입력한 프롬프트를 발화 순서대로, 최대한 원문 그대로 옮긴 것이다.** 다음 에이전트가 "왜 이 작업을 하고 있는지" 오해 없이 이해하도록 하기 위해 요약하지 않고 그대로 남긴다.

### 2-1. 첫 번째 요청 (감사 착수)

> 현재 메뉴에서 보이는 카드가 /toss-design /impeccable 이랑, @DESIGN.md, @docs 에 위배되지 않거나, 아님 실제 production에서 사용 가능한 UI/UX인지 등... (카테고리별 box 만들어서 분리하는건? 그리고 현재 메뉴 카드 방식은? 리스트 방식이나, 아님 인기 섹션/카테고리처럼 좌우 스크롤 적용?, 아님 그냥 정사각형 이미지 밑에 텍스트만 넣는 방식? 등.... 이런것들 모든걸 고려해서, 아까 말해듯이 /toss-design 를 무조건 표준으로 /impeccable 은 마지막 review할때 확인, 그리고 가장 중요한 @docs 가이드라인들: "모던함, 심플리즘"을 우선순위로, 그리고 장애인들도 일반 유저/고객들과 거의 비슷한 아님 동일한 정보와 UI, 그리고 UX를 적용하는것임.
> + 현재 모든 comps (버튼, 텍스트, 체크박스, 헤더 등...)들 각 페이지에 제대로 적용되고 있는지, AI slop이 만들어낸 유지보수 부채는 없는지 (만약 유지보수 지옥이 나올것 같은건 정확한 해결책을 직접 작성해: 함수, 파일을 나눠야한다거나, 통합한다던가, 아님 어떤 type으로 변경하거나, 코드를 어떻게 작성해야하다던가 등...)
> + 내가 아직 언급하지 않음 문제점이나, 해결방식, 그리고 코드랑 docs 읽다가 추가할것들, 제거할것들, 수정해야할것들 있으면 계획서에 그냥 편하게 최대한 많이 추가해
> + 무조건 디테일하게, 어떤거든 하나도 빠짐없이
>
> 일단 모든 코드 다 분석해서 보고, 계획만 하는거임

**핵심 지시사항 추출**:
- toss-design 스킬이 **무조건 표준**, impeccable은 **최종 리뷰 게이트**로만
- `@docs` 가이드라인의 "모던함, 심플리즘"이 우선순위
- 장애인도 일반 사용자와 **거의 동일한 정보/UI/UX**를 받아야 함(별도 모드 아님)
- 메뉴 카드가 실제 프로덕션에 쓸 수 있는 수준인지 판단
- 카테고리 박스 분리 여부, 카드 레이아웃(리스트/가로스크롤/정사각형+텍스트) 검토
- 컴포넌트 재사용 여부, AI slop으로 인한 유지보수 부채 — **발견 시 구체적 해결책(함수/파일 분리, 통합, 타입 변경 등)까지 직접 작성**
- 사용자가 언급 안 한 문제도 자유롭게 추가
- **디테일하게, 하나도 빠짐없이**
- **이 단계는 계획만 — 코드 작성 금지**

### 2-2. 이 요청에 대해 한 일

전체 코드베이스(`app/`, `components/`, `lib/`, `store/`, `hooks/`, `docs/`, `.claude/skills/toss-design`)를 정독하고, `tsc`/`vitest`/`eslint`/`next build`를 직접 실행해 검증하고, WCAG 대비비를 직접 계산(node 스크립트)해서, `docs/ux-plan-2026-08-17.md`라는 방대한 감사+계획 문서를 작성해 `SendUserFile`로 전달했다. 이 문서는 지금도 존재하며 **여전히 유효한 1차 소스**다(§3 참고).

### 2-3. 두 번째 요청 (계획 확장 + 결정)

> @docs 재개편하고, 현재 최소 2번이상 쓰이는 버튼, 카드, 등... components 같은건 모듈화 시키고, 폴더 사용해서 코드나 함수도 조금 더 나눠도 될듯.
> + 메뉴 고르는곳에서 헤더에 매장 or 포장 텍스트를 어디다 위치하고, 설정 버튼 추가하는게 좋은지 등... 이런것들도 같이 넣어주고
>
> 부록 A에서 3,5 번은 일단 보류하고 나머지만 너의 권고대로 해 + 만약 그 외 하다가 더 질문있으면 그냥 편하게 몇십개, 길게 질문해도 됨
>
> 일단 계획 추가 및 수정하고, 그 다음에 정말 모든 계획서 디테일하게 나눠서 다 작성하고 (어떻게 해야할지도 작성하면) 알려줘.

**핵심 지시사항 추출**:
- `docs/` 폴더 재개편
- 2번 이상 쓰이는 버튼/카드류 컴포넌트를 모듈화, 폴더로 코드/함수 분리
- 메뉴 화면 헤더의 매장/포장 텍스트 위치 + 설정 버튼 추가 여부 검토
- **부록 A(사용자가 결정해야 할 6개 항목) 중 3번(QrScannerModal)과 5번(언어 설정)은 보류, 나머지(1,2,4,6번)는 내 권고대로 확정**
- 질문 있으면 자유롭게(수십 개, 길게) 물어봐도 됨
- 먼저 계획서 갱신, 그 다음 **모든 계획을 파일별/작업별로 초상세하게(어떻게 해야 하는지까지) 분리해서 작성**

## 4. 감사 방법론과 신뢰도

`docs/ux-plan-2026-08-17.md` §0에 상세히 있지만 핵심만 다시 적는다:

- **직접 실행해서 검증**: `tsc --noEmit`, `vitest run`, `eslint .`, `next build` — 전부 실제로 돌려봄. 컴파일된 CSS(`.next/static/chunks/*.css`)를 grep해서 `rounded-[--radius-md]`가 무효 CSS(`border-radius:--radius-md`, `var()` 없음)로 컴파일되는 걸 직접 확인함.

## 8. 실행 중 새로 발견한 것 — 원래 계획서에 없던 정보

`docs/ux-plan-2026-08-17.md`는 코드를 실제로 고치기 전에 쓰여진 계획서라, 실행 과정에서 몇 가지 계획서엔 없던 사실이 드러났다. 다음 에이전트가 계획서만 보고 오해하지 않도록 여기 정리한다.

### 8-1. 피어 세션이 헤더/스크롤/직원호출 구조를 크게 바꿔놓았다

원래 감사(§0~12)는 아래 상태를 전제로 쓰여졌다:
- `HeaderBar`가 2단(매장명 위, 배지 아래) + `sticky top-0`
- `MenuCategoryHeader`가 `sticky top-[58px]`로 그 아래 스택
- 누적 sticky 높이 118px

**실제로는(피어 세션이 바꿔놓은 상태, 이 세션이 그 위에서 작업함)**:
- `HeaderBar`가 1단(좌: 뒤로가기+매장명, 우: 배지) + **더 이상 sticky가 아님**(페이지와 함께 스크롤되어 사라짐)
- `MenuCategoryHeader`만 `sticky top-0`으로 남음, 실측 높이 약 60px
- `StaffCallButton`에 스크롤 방향에 따라 펼침/접힘(`isExpanded` prop)되는 새 인터랙션이 추가됨 — `MenuClientView`가 `lastScrollY` ref와 `isStaffCallExpanded` state로 이걸 구동함. **이 인터랙션은 건드리지 않았고, 앞으로도 의도적으로 보존해야 한다** — 나쁜 패턴이 아니라 엄지 영역 절약을 위한 합리적인 신규 기능이다.
- `StaffCallButton`과 `CartSummaryPill`이 이제 `MenuClientView`가 렌더하는 하나의 하단 고정바(`fixed bottom-... flex items-center gap-3`) 안에 형제로 같이 들어감(이전엔 각자 독립적으로 `fixed` 포지셔닝했음)

**이 세션이 한 일은 이 새 구조 위에서 스크롤스파이를 고쳤다**(§6, Phase 1.5/1.6). 원래 계획서 §6.8이 설명하는 "118px 누적 스택" 전제는 더 이상 안 맞지만, 그 섹션이 지적한 근본 문제(하드코딩된 매직넘버, 짧은 섹션에서의 깜빡임)는 여전히 유효했고 그걸 고쳤다.

**`docs/ux-plan-2026-08-17.md`의 §16(헤더 레이아웃 결정)이 전제한 "grid-cols-[44px_1fr_44px]" 3분할 구조는 실제로 구현하지 않았다** — 대신 피어 세션이 이미 만들어놓은 `flex items-center justify-between` 2그룹 구조(좌: 뒤로가기+이름, 우: 배지+설정) 위에 설정 버튼을 자연스럽게 추가하는 쪽을 택했다. §16이 원하는 **결과**(44px 설정 버튼 존재, 44px 뒤로가기, 배지 aria-hidden+대비 확보)는 전부 달성했지만, **레이아웃 구현 방식(grid 3분할 vs flex 2그룹)은 계획서와 다르다.** 다음 에이전트가 §16을 읽고 "왜 grid-cols가 아니지?"라고 헷갈리지 않도록 여기 명시해둔다. 지금 구조가 더 낫다고 판단했다(피어 세션의 기존 작업을 존중, 불필요한 재작업 회피).

### 8-2. `outline-none` 단독 사용(ring 없이) — 원래 §6.2 grep이 못 찾은 것들

원래 계획서 §6.2는 `outline-none` **+** `focus-visible:ring-*`가 **같이** 있는 경우만 grep으로 찾았다(`rg "outline-none" | grep "focus-visible:ring"`). 이번 세션에서 그 15곳을 전부 고쳤다(§6 참고). 그런데 **`outline-none`만 단독으로(어떤 ring 대체물도 없이) 붙어있는 곳**은 원래 계획서에 없던 별도 카테고리이고, 이건 **아직 하나도 안 고쳤다.** 이런 요소는 키보드 포커스 시 시각적 표시가 **완전히 없다**(2.17:1도 아니고 0 — 위에서 고친 것보다 오히려 더 심각할 수 있음). 정확한 목록은 §9-1에 있다.

### 8-4. `bg-primary/10` 잔존 현황 — 어디까지가 진짜 문제였는지

## 9. 다음 단계 — 정확히 어디서부터 재개할지

**가장 먼저 할 일**: `git status --porcelain` 재확인 → 위 §7 목록과 다르면(누군가 또 편집했다면) 달라진 파일을 다시 읽고 이 문서의 서술과 어긋나는 부분이 있는지 확인. 그 다음 `docs/ux-plan-2026-08-17.md` §18을 열어서 Phase 2부터 이어서 읽을 것(Phase 0/1은 완료, Phase 2는 부분 완료).

### 9-1. Phase 2 나머지 (원래 계획서에 없던, 이번에 새로 발견한 항목 포함)

**A. `outline-none` 단독 사용 완전 정리 (신규 발견, §8-2)** — 다음 파일들에서 `outline-none`이 어떤 focus-visible ring 대체물도 없이 단독으로 붙어있어서, 포커스 시 시각적 표시가 전혀 없다:
- `app/settings/page.tsx:122, 282` — 글자크기/언어 선택 세그먼트 버튼(2곳, 같은 패턴)
- `components/flow/A11yToastContainer.tsx:99` — 토스트 안의 "취소"(undo) 버튼
- `components/flow/TableSelectView.tsx:89` — 테이블 번호 선택 버튼
- `components/settings/SettingsRow.tsx:72` — `SettingsRow`의 링크/버튼 아닌 plain div 케이스(포커스 가능 요소가 아니면 실질 위험 없음, 확인 필요)
- `components/ui/tabs.tsx:84` — `TabsContent`(죽은 컴포넌트, 낮은 우선순위)

처리 방법은 지금까지와 동일: `outline-none` 제거하면 전역 `:focus-visible` 규칙이 자동으로 살아난다.

**B. 나머지 `dark:` 4곳 정리(§8-3)** — `ProductDetailSheet.tsx:171`을 우선, `switch.tsx`/`tabs.tsx`는 Phase 7에서 파일째 삭제되니 그때 자연 해소, `badge.tsx`의 destructive/ghost variant는 여유 있을 때.

**C. 원래 계획서 §18 "Phase 2" 항목 중 아직 안 한 것들**:
- **2.9 품절 상품 포커스 가능화**: `components/flow/ProductCard.tsx`의 `disabled={!product.available}`를 `aria-disabled={!product.available}`로 바꾸고, `onClick` 핸들러 안에서 `if (!product.available) return;`으로 클릭만 막기. 지금은 품절 상품이 `disabled`라서 Tab 순서에서 완전히 빠지고, 스크린리더 사용자는 그 상품의 존재 자체를 모른다.
- **2.4~2.8은 이번 세션에서 대부분 완료됨**(§6 참고) — 재확인만 하면 됨. 단, 원래 §7.1 표에 있던 대비 실패 목록 중 아직 안 건드린 것 있는지 `docs/ux-plan-2026-08-17.md` §7.1 표와 대조해서 재확인할 것(포커스 링 관련 2건은 이번에 다 고쳤지만, 그 표에 있던 나머지 항목들 — 예: `SettingsRow`의 `text-muted-foreground/70` 셰브런 3.45:1 같은 것 — 은 손 안 댔을 수 있음, 재확인 필요).

### 9-2. Phase 3 — 토스트/피드백 아키텍처 (미착수, P0)

`docs/ux-plan-2026-08-17.md` §18의 Phase 3 섹션을 그대로 따를 것. 핵심: `/settings`에서 토글을 바꿔도 **시각적 토스트가 전혀 안 뜨는** P0 버그(`notify()`가 반환만 하고 스토어에 안 넣음, `<A11yToastContainer />`가 `MenuClientView` 안에만 마운트되어 있어서 설정 라우트엔 토스트 UI 자체가 없음)를 고쳐야 한다. `useToastStore.ts` 분리, `A11yFeedbackService`를 `announce()`/`toast()` 2함수로 재설계, `A11yToastContainer`를 `app/layout.tsx`로 이동. 상세 절차는 계획서 §18 Phase 3의 6개 세부 항목(3.1~3.6) 그대로.

### 9-3. Phase 4 — 컴포넌트 폴더 재구성 + 추출 (미착수)

`docs/ux-plan-2026-08-17.md` §15(전체 트리)와 §18 Phase 4(4.1~4.9)를 그대로 따를 것. `components/shared/` 신설, `flow/` 21개 파일을 도메인 서브폴더로 이동, `BackButton`/`SettingsIconButton`/`StickyActionBar`/`QuantityStepper`/`SelectionCard` 추출, `SettingsRow.tsx` 3분할.

### 9-4. Phase 5 — 메뉴 카드 재설계 (미착수, 핵심)

`docs/ux-plan-2026-08-17.md` §3(전체 스펙, 옵션 비교, 최종 권고)과 §18 Phase 5(5.1~5.9)를 그대로 따를 것. **이게 원래 사용자의 첫 질문("메뉴 카드가 프로덕션에 쓸 수 있는 수준인지")에 대한 직접적인 답**이다 — 지금 카드는 사진 위에 유리패널로 텍스트를 얹는 구조라 대비 보장이 물리적으로 불가능하다(§1.1, §2 참고). B안(사진 위 4:3 + 텍스트 아래, 토큰 배경) 기본 + fontScale≥1.15에서 C안(1열 리스트)으로 자동 전환하는 게 확정된 결정이다.

`docs/ux-plan-2026-08-17.md` §18의 해당 섹션 그대로. 순서: 로딩/에러/데이터 레이어 → 죽은 코드 정리(QrScannerModal/언어 설정은 계속 보류 유지) → 회귀 방지 테스트(`design-tokens.test.ts` 신설 — 이게 있었으면 §8-2에서 발견한 "outline-none 단독" 문제를 자동으로 잡았을 것) → docs 재개편 실행(§14) → 최종 리뷰(`/impeccable audit`, `/impeccable critique`).

## 10. 환경/툴링 노트 (함정들)

- **dev 서버가 이미 떠 있음**: 이 세션 시작 시점에 `localhost:3000`에서 `next dev`가 이미 실행 중이었다(다른 프로세스/세션이 띄워놓은 것으로 추정). `preview_start`로 새로 띄우려 하면 "Another next dev server is already running" 에러가 난다 — `preview_start`에 `{url: "http://localhost:3000"}`으로 기존 서버에 붙는 방식을 쓸 것.
- **Lenis가 프로그래매틱 스크롤을 가로챈다**: §6 마지막 문단 참고. `window.scrollTo()`나 합성 이벤트로 스크롤 테스트하지 말 것.
- **브라우저 자동화 도구(`computer` 액션)가 이 세션에서 간헐적으로 타임아웃/블랭크 스크린샷을 반환했다** — "Browser pane is currently hidden" 에러. 재현 원인 불명(코드 문제 아님, 툴링 환경 이슈로 추정). `javascript_tool`(JS 직접 실행)과 `read_page`/`get_page_text`는 훨씬 안정적으로 작동했다 — 픽셀 단위 시각 확인이 꼭 필요한 게 아니면 이쪽을 우선 쓸 것.
- **`SettingsCard`의 트레일링 아이콘 함정**(계획서 §13에 이미 기록됨, 아직 안 써먹었지만 Phase 7에서 필요): `trailing ?? <ChevronRight />`가 기본값인데, `trailing={null}`을 넘겨도 `??`는 `null`을 nullish로 취급해서 여전히 ChevronRight가 뜬다. 진짜로 숨기려면 `trailing={<span className="sr-only">...</span>}`처럼 빈 시각 요소를 명시적으로 넘겨야 한다.
- **`bun`이 패키지 매니저**지만 이 세션에서는 `npx`로 tsc/vitest/eslint/next를 직접 호출했다(둘 다 동작함, `node_modules`가 이미 설치되어 있어서 npx가 로컬 바이너리를 찾아 씀). `bun install`/`bun run`으로 전환해도 무방.
- **테스트 환경(jsdom)의 알려진 무해한 경고**: `Not implemented: HTMLCanvasElement's getContext()`(canvas-confetti가 못 찾는 것, `vitest.setup.ts`에서 이미 mock 처리됨에도 일부 경로에서 뜸), `Not implemented: Window's scrollTo()`(jsdom이 실제 스크롤을 구현 안 함) — 둘 다 테스트 실패 원인 아니고 항상 나오던 잡음이다. 매번 결과 하단의 실제 `Test Files`/`Tests` 통과 카운트만 보면 됨.
