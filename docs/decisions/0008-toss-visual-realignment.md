# 0008 — Toss visual realignment: token-level, via the merged Figma + brand-guide reference

**Status:** Accepted

## Context

ADR 0005 already decided *how* Toss's feel would be achieved — a design-token layer on top of shadcn + Radix, not the `@toss/tds-mobile` component library itself — but it worked from Toss's feel as generally understood, not from Toss's actual documented design system. Two concrete new sources changed that: an official Toss Design System Figma file (`TDS_Mobile_for_Apps_in_Toss_(2602-3-2).fig`) and a separate written Toss brand guide, both merged, contradiction-resolved, and packaged as a persistent Claude Code skill (`.claude/skills/toss-design`, mirrored to `~/.gemini/config/skills/toss-design`) ahead of this pass. That skill's reference doc (`reference/TDS_Toss_Merged_Design_System.md`) is now the literal source of truth this ADR draws from — not a general impression of "the Toss look."

The two source documents disagreed with each other on several concrete values (primary blue hex, button radius, body-text weight floor, semantic color pairs); those were already resolved once, explicitly, inside the merged reference's own §0 before this pass started. This ADR is about the *second* layer of conflicts: where the resolved Toss values disagree with Jumun's own prior, independently-verified accessibility commitments (`docs/design-system.md`).

Three such conflicts were found during implementation, verified by computing actual WCAG contrast ratios rather than assuming Toss's tokens would clear this product's floors:

1. **Primary blue as text/fill**: Toss's canonical `#0064FF` computes to 4.92:1 on white — clears the enforced 4.5:1 default-mode floor, but with far less headroom than the prior `#1A56B0` (7.45:1).
2. **Error red as text**: Toss's literal `error-fg` (`#FF4040`) computes to only 3.47:1 on white — **fails** the 4.5:1 floor as the small button/badge text this codebase actually renders it as (Toss's own component spec uses it as a filled-button background with white text, or as icon/large-surface color — not as this codebase's `text-destructive` pattern).
3. **Success green as text**: Toss's literal `success-fg` (`#00A85A`) computes to 3.11:1 on white — also fails 4.5:1, same root cause as (2). Not currently wired as a live text color in this codebase, so no immediate fix was needed, but flagged for whoever wires it up next.
4. **Pure white/black avoidance**: the *prior* design system (`docs/design-system.md` spec rule 5, pre-dating this ADR) explicitly avoided pure `#FFFFFF`/`#000000` backgrounds, reasoning that they cause glare/afterimage for low-vision and elderly users. Checked against `PRODUCT.md` and `plan.md` before touching this rule: neither document mandates it — it was `docs/design-system.md`'s own prior interpretation, not a literal stakeholder requirement.

## Decision

Adopt the Toss token set from `reference/TDS_Toss_Merged_Design_System.md` at the CSS-custom-property layer (`app/globals.css`'s `:root`), and everywhere those tokens are consumed by component classes (`components/ui/{button,card,badge,dialog,drawer}.tsx` and the handful of components with hardcoded hex tied to the old blue: `CartSummaryPill.tsx`, `QrScannerModal.tsx`, `ConfirmationStep.tsx`'s confetti palette) — **except** where a literal Toss value would drop below this product's 4.5:1 contrast floor as actually used in this codebase. Concretely:

- Primary blue: adopted literally (`#0064FF`), accepting the reduced-but-still-compliant headroom — this is a text/fill color used pervasively and consistently, and 4.92:1 is a real, verified pass, just a tighter one.
- Destructive red: **kept** the prior `#B91C1C` (6.47:1) rather than adopting Toss's `#FF4040` (3.47:1) — this codebase renders it as direct small text (`text-destructive` on `button.tsx`/`badge.tsx`'s destructive variants), a usage pattern Toss's own spec doesn't put its error-fg token in. Toss's status colors are explicitly not brand-identity-bearing in Toss's own system (only the blue is) — keeping this one token off-spec doesn't compromise "looking like Toss" in any way a viewer would notice, and avoids a real, machine-checkable accessibility regression (`vitest-axe`'s color-contrast rule would have caught this had it shipped).
- Success green: documented at Toss's literal value (`#00A85A`, used today only for the order-confirmation confetti, which carries no contrast requirement) with an explicit caveat against wiring it up as a live text color without the same substitution treatment as destructive.
- Pure white/black background: adopted literally — Toss's own spec, and no longer overridden the way the prior "Well-Lit Counter" system deliberately did. This is the one change in this ADR that isn't forced by a measurable WCAG failure; it's a judgment call, made because (a) it wasn't a literal product requirement to begin with (checked, see Context §4) and (b) the actual contrast floors (rule 1) are unaffected — text-on-white ratios stay 16+:1 regardless of whether the white is "pure." If user testing ever surfaces a real glare/afterimage complaint from the actual target audience, revisit this specific token first.
- Card treatment: moved from a color-shifted "warm oatmeal" surface (`docs/design-system.md`'s prior Never-Alone Rule) to Toss's literal white-on-white-plus-border-and-shadow treatment (**Border-and-Shadow Rule**, `DESIGN.md`) — a visual change, not an accessibility one; boundary legibility is preserved by two cues either way.
- Button radius: flattened to a uniform 12px (`--radius-md`) at every height, replacing the prior height-scaled radius (up to 20px at CTA height) — Toss's own anti-pattern explicitly treats 12–14px as a fixed signature band regardless of button size.

The NFC/QR hero animation (`components/flow/LandingHeroVisual.tsx`) was explicitly out of scope for this pass by direct instruction and verified to need zero changes — it's fully token-driven via `currentColor`/`text-foreground`/`fill-background`, so it re-themes automatically.

## Consequences

- Every color, radius, and shadow token in `app/globals.css`, `DESIGN.md`, and `docs/design-system.md` now traces to a specific, citable source: either `reference/TDS_Toss_Merged_Design_System.md` (with a section reference) or an explicit "kept from the prior verified value, here's why" note. No token in this pass was chosen without a documented reason.
- The accent blue's contrast headroom is now measurably thinner (4.92:1 vs. the prior 7.45:1) — still a real pass of this product's enforced floor, but a fact worth remembering if any future change (e.g., a lighter-weight or smaller rendering of blue text) is considered; it has less margin to absorb further erosion than any other token in the palette.
- `docs/design-system.md`'s color/typography/radius/elevation tables were rewritten with freshly-computed ratios rather than assumed-still-correct carried-over numbers — this also fixed two pre-existing, unrelated drifts discovered along the way: the elevation table's rgba base color no longer matched `app/globals.css` (`rgb(33,30,26)` documented vs. `rgb(17,24,39)` shipped), and the AAA-mode prose claimed accent/primary "is not redefined" for high-contrast mode when the code has always redefined it.
- `.claude/skills/toss-design`'s reference material becomes an active, load-bearing part of this project's design provenance, not just a standalone reference bundle — future visual work on Jumun should treat that skill's merged doc as the first citation, the way this ADR does.

## Alternatives considered

- **Adopt every Toss token literally, no exceptions.** Rejected — this would have shipped a verified WCAG AA failure on the destructive button/badge text color (3.47:1 against a 4.5:1 floor), the exact failure mode `docs/testing-strategy.md`'s axe-core gate exists to catch. "Match the reference" was never a license to ship a measurable accessibility regression the reference itself doesn't actually require (Toss's own component spec doesn't use error-fg as small text either).
- **Keep the prior blue (`#1A56B0`) and only adopt radius/shadow/spacing.** Rejected — the whole point of this pass was to stop approximating Toss and start citing it; keeping a non-Toss blue while calling the system "Toss-aligned" would misrepresent the provenance the merged skill reference is meant to establish.
- **Re-derive a custom darker blue that clears 7:1 like the old accent did, instead of adopting `#0064FF` literally.** Rejected for the primary token — 4.92:1 is a genuine, verified pass of this product's actual enforced floor (4.5:1, not 7:1, in default mode; see `docs/design-system.md`'s "Floor vs. actual" framing), and diluting the one color a viewer would actually recognize as "Toss Blue" defeats the purpose of this realignment more than the reduced headroom costs.
